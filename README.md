# MediKiosk

**AI-assisted, multilingual patient case-taking kiosk — lightweight prototype for Smart India Hackathon 2026, Problem Statement 26047 ("Patient Case-Taking Software"), Ministry of AYUSH.**

> This is a **demonstration prototype**, not a production medical system. It does not connect to OpenEMR, ABHA, FHIR, or any hospital database. It does not diagnose, prescribe, or provide medical advice. See [Disclaimer](#disclaimer).

---

## What it does

MediKiosk simulates a hospital self-service kiosk that takes a patient's history *before* they see a clinician:

1. **Welcome → Language → Interaction mode → Consent → Pathway → Demographics** — a short, accessible onboarding flow.
2. **AI-assisted interview** — a conversational, adaptive question sequence (8–12 questions) covering presenting complaint, history, medications, allergies, family history, and lifestyle, with extra AYUSH lifestyle questions when the patient selects the Ayurvedic pathway. Powered by Groq, with a **fully offline fallback** question engine if Groq is unavailable. Free-text answers are automatically checked for relevance by Grok (xAI) before being accepted — see below.
3. **"Anything else to add?"** — after the last required question, the kiosk asks once more and lets the patient add free-text notes (or skip straight to review).
4. **Review screen** — the patient can edit any answer, and attach documents that can actually be opened later (see Document viewing).
5. **Red-flag screening** — a transparent, rule-based check (e.g. chest pain + breathlessness) that is never delegated to any AI.
6. **AI clinical summary** — a structured, physician-facing summary generated by Groq (with a factual, template-based fallback if Groq is unavailable).
7. **Success screen** — a unique queue number and status, like a real kiosk.
8. **Doctor dashboard** (`/doctor`) — no login required for the demo — showing a persistent, additive patient queue (seeded demo patients + every real submitted intake), red-flag counts, and a per-patient clinical view (summary, timeline, symptoms, medications, additional notes, viewable documents, AI notes).

## Tech stack

- **React 18 + Vite + TypeScript**
- **Tailwind CSS** for styling
- **React Router** for navigation
- **lucide-react** for icons
- **Groq API** (OpenAI-compatible `/chat/completions`) for the dynamic interview and clinical summary
- **xAI Grok API** (OpenAI-compatible `/chat/completions`), used *only* for classifying whether a free-text answer is relevant to the question asked — a completely separate integration from Groq
- **No database.** Active intake lives in React state, mirrored to `localStorage` only so a page refresh doesn't wipe an in-progress demo session. The doctor-dashboard patient queue is also `localStorage`-backed and purely additive.
- **Serverless functions** (Vercel API routes, with a Netlify Functions equivalent) keep `GROQ_API_KEY` and `XAI_API_KEY` server-side only — neither is ever exposed to the browser.

No Firebase, Supabase, Mongo/Postgres/MySQL, OpenEMR, Docker, Python/PHP backend, Redis, or paid APIs are used.

## How it works

### Groq integration (question generation + summary)
The browser never talks to Groq directly. `src/services/groq.ts` calls `POST /api/chat` and `POST /api/summary`, which are serverless functions that read `GROQ_API_KEY` from server-side environment variables and forward a tightly-scoped system prompt (see `lib/groqServer.ts`) instructing the model to act **only** as an intake assistant — never diagnosing, prescribing, or claiming medical certainty — and to reply with the exact language and JSON shape the UI expects.

### Grok (xAI) integration — response relevance classification only
This is a **separate integration** from Groq. `src/services/relevance.ts` calls `POST /api/classify`, a serverless function that reads `XAI_API_KEY` server-side (`lib/grokServer.ts`) and asks Grok exactly one narrow question: *does this free-text response reasonably answer the question that was asked?* It is explicitly instructed to never diagnose, interpret symptoms, or judge medical seriousness. It's only invoked for free-text interview answers — button/card selections, language, and pathway choices never call any AI classifier. If the response is judged irrelevant (e.g. "hi", "what do you mean"), the kiosk shows a spoken clarification and asks again, offering "Skip for now" after two failed attempts. If Grok is unreachable, misconfigured, or returns malformed JSON, the classifier fails open — the patient's answer is accepted without blocking the intake.

### Automatic + manual text-to-speech
Every assistant question (including the dynamic "anything else to add?" step and relevance clarifications) is automatically read aloud via `window.speechSynthesis` the moment it appears, using a voice matched to the selected language where the browser has one. A ref-based guard (`lastSpokenTurnId`) ensures each message is spoken exactly once, never repeated by re-renders, and any prior utterance is cancelled before a new one starts. The manual speaker button next to the input remains for replaying a question on demand.

### Multilingual intake
Static UI copy (buttons, labels, screens) comes from a hand-written dictionary in `src/data/translations.ts` for English, Hindi, and Marathi — this never depends on a network call. The dynamic interview questions are generated by Groq in the selected language; the system prompt explicitly names the target language. Adding a new language is one entry in `translations.ts` plus `languageMeta` — nothing else changes.

### Voice input
`src/components/VoiceInput.tsx` uses the browser's native `SpeechRecognition` (or `webkitSpeechRecognition`) API with no external speech service. Support is detected at runtime; if it's missing, the microphone button simply doesn't render and text input is always available.

### Fallback / demo mode
If `GROQ_API_KEY` is missing, the network request fails, Groq is rate-limited, or the response can't be parsed into the expected shape, `src/services/groq.ts` transparently switches to:
- `src/data/fallbackQuestions.ts` for the interview — a deterministic, adaptive question sequence (it still branches on "chest pain" / "headache" mentions), and
- a locally assembled, purely factual summary template for `/review` → `/complete`.

The patient sees a small "AI assistance temporarily unavailable — continuing with guided intake" notice, but the flow never breaks. The Grok relevance classifier degrades the same way: any failure simply lets the response through. **The app is fully usable with zero Groq/xAI configuration** — this is exactly what happens under plain `npm run dev`, since Vite alone doesn't serve the `/api/*` routes (use `vercel dev` to exercise the real integrations locally).

### Red-flag screening
`src/services/redFlag.ts` is a small, transparent, rule-based check (e.g. chest pain + breathlessness/sweating, or chest pain + a cardiovascular risk factor). It runs entirely client-side on the collected answers and is **never** delegated to any AI. It is always labelled "Prototype safety screening — not a diagnosis."

### Doctor dashboard queue (additive, persistent)
`src/services/patientQueue.ts` stores completed intakes in `localStorage` under `medikiosk_patients`. Every submission is **appended** — the three seeded demo patients (queue numbers A-024 to A-026) are never overwritten, and each new intake gets the next sequential queue number (A-027, A-028, ...). The dashboard combines the seeded list with whatever has been persisted and renders both.

### Document viewing
`DocumentUpload` creates a real `URL.createObjectURL()` for every uploaded file, so it can be opened again later in the same browser session. `DocumentViewer` (used on both the patient review screen and the doctor dashboard) renders images inline and PDFs via an `<iframe>`, with a close button and no external PDF library. Seeded demo patients don't have real scanned files, so their document cards use a small generated "sample document" placeholder image, clearly labelled as demo data — clicking **View** still opens something real rather than doing nothing.

**Limitation:** object URLs only live for the current browser tab/session — they are not persisted across a hard page refresh. This is intentional for a database-free prototype; see the note in `src/services/patientQueue.ts` for how this would be swapped for real object storage.

## Local setup

```bash
npm install
npm run dev
```

The app runs at `http://localhost:5173` and works immediately with no configuration — it will use the local fallback question engine and summary template until you add a Groq key.

To exercise the real Groq and Grok integrations locally, use the Vercel CLI so the `/api/*` routes are served alongside the frontend:

```bash
npm install -g vercel
vercel dev
```

### Environment variables

Copy `.env.example` to `.env` and fill in:

| Variable | Description |
|---|---|
| `GROQ_API_KEY` | Your Groq API key from [console.groq.com](https://console.groq.com). Never commit this. |
| `GROQ_MODEL` | Any current Groq-hosted model, e.g. `llama-3.1-8b-instant`. See [console.groq.com/docs/models](https://console.groq.com/docs/models) for the up-to-date list. |
| `XAI_API_KEY` | Your xAI API key from [console.x.ai](https://console.x.ai). Powers the free-text relevance classifier only. Never commit this. |
| `XAI_MODEL` | Any current Grok model, e.g. `grok-4-fast`. See [docs.x.ai/docs/models](https://docs.x.ai/docs/models) for the up-to-date list. |

## Deployment

### Vercel (recommended)

1. Push this project to a GitHub repository.
2. Go to [vercel.com/new](https://vercel.com/new) and import the repository.
3. Framework preset: **Vite** (should be auto-detected).
4. Under **Environment Variables**, add:
   - `GROQ_API_KEY` = your key
   - `GROQ_MODEL` = `llama-3.1-8b-instant` (or your preferred model)
   - `XAI_API_KEY` = your key (optional — the relevance classifier fails open without it)
   - `XAI_MODEL` = `grok-4-fast` (or your preferred model)
5. Deploy. Vercel automatically builds `api/chat.ts` and `api/summary.ts` as serverless functions — no extra configuration needed (see `vercel.json` for the SPA rewrite rule).
6. Visit the deployed URL — the kiosk, interview, and doctor dashboard are all live.

_(Or via CLI: `npm install -g vercel && vercel` from the project root, then `vercel --prod`.)_

### Netlify

1. Push the project to GitHub.
2. Go to [app.netlify.com](https://app.netlify.com) → **Add new site → Import an existing project**.
3. Build command: `npm run build`. Publish directory: `dist`. (Already set in `netlify.toml`, which also wires up `/api/chat`, `/api/summary`, and `/api/classify` redirects to the functions in `netlify/functions/`.)
4. Under **Site settings → Environment variables**, add `GROQ_API_KEY`, `GROQ_MODEL`, and optionally `XAI_API_KEY` / `XAI_MODEL`.
5. Deploy.

### Render (fallback only)

Only use this if Vercel/Netlify serverless functions cause problems in your environment:

1. Create a **Static Site** on [render.com](https://render.com) for the frontend: build command `npm run build`, publish directory `dist`.
2. Since Render's static sites can't run serverless functions, either:
   - Skip a live Groq/Grok backend entirely — the app works fully on the local fallback engine, or
   - Deploy a minimal Node web service on Render that re-exports the logic in `lib/groqServer.ts` and `lib/grokServer.ts` behind three routes (`/api/chat`, `/api/summary`, `/api/classify`) using a tiny Express wrapper, and point the frontend's fetch calls at that service's URL.
3. Add `GROQ_API_KEY` / `GROQ_MODEL` / `XAI_API_KEY` / `XAI_MODEL` as Render environment variables if you deploy the backend service.

## Demo mode

MediKiosk is designed to be deployed **before** you ever configure Groq or xAI. With no `GROQ_API_KEY` or `XAI_API_KEY` set, every API call fails fast and the app falls back to the local question engine, summary template, and permissive relevance check — the UI, routing, red-flag screening, voice input, document upload/viewing, and doctor dashboard all work exactly the same. This lets you ship the UI first and wire up the AI providers later without redeploying architecture.

## Limitations (by design, for this prototype)

- No real database, authentication, ABHA/OTP, OpenEMR, or FHIR integration.
- Document upload uses simulated OCR extraction — no real text is extracted from files. Document *previews*, however, are real: uploaded images/PDFs are genuinely viewable via `URL.createObjectURL()`, but those object URLs only last for the current browser tab session and won't survive a hard refresh.
- The Grok relevance classifier judges topical relevance only — it never assesses medical seriousness, and it fails open (lets the answer through) if xAI is unreachable or unconfigured.
- Red-flag screening is a small illustrative rule set, not a validated clinical decision system.
- AYUSH Dosha-style assessment (if shown) is explicitly labelled "Demonstration assessment only."
- Session data and the doctor-dashboard patient queue live only in `localStorage` on the current device/browser — this is not a patient record system.

## Disclaimer

MediKiosk is a patient history-taking and documentation prototype. It does not provide medical diagnosis or treatment. Clinical decisions must be made by qualified healthcare professionals. All patient data shown (including "Rahul Sharma" and other dashboard entries) is fictional demonstration data.

## Voice-first patient kiosk UI

The patient flow is now voice-first after language selection. The interaction-mode screen is no longer used. Patient answers are captured through browser speech recognition, shown as editable text, and submitted with a single Continue action. Questions are spoken aloud when speech synthesis is available.

For the kiosk, use a current Chromium-based browser such as Google Chrome and allow microphone access. Browser speech-recognition support and automatic microphone startup can vary by browser/security policy; the microphone button remains available as a fallback.
